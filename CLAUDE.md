# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is the Herdr desktop app's home folder (`~/.config/herdr-app`) under git, not an application codebase. The running app redraws itself from these files within a second of a change. **`AGENTS.md` is the authoritative manual** (layouts, keys, commands, mod API); read it before changing anything structural. Don't edit `AGENTS.md`, `herdr.d.ts` or any `gpui-kit.d.ts`: the app rewrites them on every start.

There is no build or lint setup. Mods are plain JavaScript (gpui-kit) that Herdr loads and hot-reloads directly; TypeScript and bundling are not part of the workflow. Unit tests (spec 025) use Node's built-in `node:test`, no `package.json`: they live in `tests/*.test.mjs` (never under `mods/`), test the single source in `lib/` (not the synced copies; a mod's own unsynced logic file such as `mods/pr-flow/tracker.js` may be imported, never written), and replace shell with a fake `exec` and the `herdr` module with `tests/herdr-stub.mjs` (`stub({ spaces, panes, focused, ... })`; `tests/setup.mjs` maps the import). Screen drawing is not unit tested; `herdr-app check` and `herdr-app shot` stay the gate there.

## Commands

```sh
herdr-app check mods/<name>     # load + render a mod once; must pass before calling a mod done
node --import ./tests/setup.mjs --test 'tests/*.test.mjs'  # unit tests of lib/ and scripts/; run after changing them
herdr-app status                # layout, focus, overlays, and errors from files/mods
herdr-app shot [file.png]       # PNG of the last rendered window frame, for checking UI
herdr-app commands              # every app command and its arguments
herdr-app do <command> '{json}' # run an app command from the shell
```

After each edit, check the matching `<name>.error` file (`layout.error`, `keys.error`, `settings.error`, `programs.error`): an invalid file is ignored and the last good version keeps running.

## Layout of the setup

The window is `layouts/tiendvd-layout.json`, a tree of `row`/`column`/`stack`/`block` nodes. Each block names a mod. The pieces wired together:

- Left sidebar: `my-chrome` (brand and footer), `better-sidebar`, `my-agents`, `inbox`.
- Work column: `my-tabs` (tab bar), then `content` (tab panes), then a right `panel-body` stack of `files` (mod `file-icons`) / `issues` / `threads`, then `status-usage` as the status bar. Changes (`reviewer`), Git (`git-graph`) and Pull requests (`pr-flow`) are not in the panel: the tab bar opens each as a 0.75×0.8 dialog with `mod.open` (again closes it; `mod.json` `overlay` with `frame: "none"`, so the mod draws the only frame with the kit's `dialogFrame`). While open, shared `reviewer.dialog` / `git-graph.dialog` / `pr-flow.dialog` holds the overlay id (set in `init`, cleared in `close()`) and lights the tab bar button. Spec: `specs/016-pr-git-dialogs/`. Project Settings (`project-settings`) is the same kind of dialog, opened from the sidebar footer row (`my-chrome`) and the + menu's `Project skills…` (`my-new-menu`, which also sets `project-settings.tab`); its Close and Ports' go-to-terminal close the dialog; flag `project-settings.dialog`. Spec: `specs/017-project-settings-dialog/`. Its sections (Ports, Worktree script, Summary prompt, Skills, Index, Memory) are a second sidebar between the projects and the content, with the project name on top (`SECTIONS` + `selectSection` in `main.js`; spec 030). Processes (`processes`, from the status bar's proc badge) opens the same way, `frame: "none"` + the kit's `dialogFrame` (spec 020). Its header shows the sessions' CPU and RAM against the machine totals and the whole machine's use (`CPU 1% sessions · 142% machine / 800%`), each over a two-layer progress bar (machine faint, sessions solid; ≥ 80% of the machine in the alert color). Totals: `sysctl`, read once per open (`mods/processes/totals.js`); machine use comes with the `procs` poll in `status-usage` (`collect()`: CPU from CPU-time growth of all processes, RAM from `vm_stat` as Activity Monitor counts it; `procs.js`). Spec 028. Open in Zed / VS Code (`open-zed`, `open-vscode`) too. Audit of every dialog: `specs/021-dialog-border-audit/research.md`.
- **Dialog border rule** (spec 024): a dialog's frame is drawn by Herdr *or* by the mod, never both, never neither. A mod that draws its own puts `overlay.frame: "none"` in `mod.json` and wraps its dialog root in the kit's `dialogFrame` (no hand-made border/rounded/shadow). Other mods open it with `run("mod.open", { name })` (reads `mod.json`; again closes it), not `openOverlay`, which ignores `mod.json` and would add Herdr's frame. Every other personal dialog too (a mod's own sub-dialogs like the diagram viewer, reviewer Ask, git-graph's action/update dialogs, `my-worktree`) opens with `frame: "none"` and wraps its root in `dialogFrame`: Herdr's rounded frame does not clip the mod's square background, so it pokes out at the corners. Only popups/menus keep Herdr's frame; a `layout` dialog (sub-agent peek) draws its frame in the layout. After adding or changing a dialog run `node scripts/check-dialog-frames.mjs` (must print `dialog frames ok`) next to `herdr-app check`.
- Sub-agent peek: clicking a sub-agent in `my-agents` no longer runs Herdr's `terminal.peek` (its shipped `peek` bar has a square background that pokes out of the dialog's rounded corners). It opens a `frame: "none"` dialog whose `layout` is a bordered, `radius: 10` column of `my-peek` (clone of `peek`, bar with `rounded_t(10)`; ✕ closes the top dialog) and the terminal. Ctrl-click on a terminal address still uses Herdr's own peek.
- Session names (specs 032, 033): one rule names a Claude session in the tab bar (`my-tabs`), the sidebar agent rows (`my-agents`) and the Sessions dialog (`processes`): a tab name the user chose; else the `/rename` title; else Claude's own title; else the live terminal title; else the first message; else the stored tab name. A name equal to a title the terminal ever had (the Threads panel names resumed tabs that way, cut to 28 chars) counts as automatic. `my-agents` reads each local session's transcript every 5 s (re-reading `~/.claude/sessions/<pid>.json`, since `/clear` changes the session) and shares the titles as `session.titles` (address → titles, written only on change; old titles kept after `/clear`). Display only, the stored name never changes. Logic: `lib/tab-title.js` (synced, tests in `tests/tab-title.test.mjs`).
- Keys live in `keys.json` (macOS `cmd-*` bindings; `tmux-prefix` mod adds a prefix mode).

## Mods: what is yours and what isn't

- **Shipped mods are Herdr's and are overwritten on update** (`spaces`, `files`, `tabs`, `menu`, `pane`, `picker`, `worktree`, ...). Never edit them in place: `herdr-app do mod.clone '{"name":"x","as":"my-x"}'`, edit the clone, and point the layout's `content.mod` at it.
- **Personal mods**: `my-tabs`, `my-agents`, `my-chrome`, `my-new-menu`, `my-worktree` (clones of shipped ones), plus `issues`, `threads`, `reviewer`, `processes`, `project-scripts`, `project-settings`, `status-usage`, `branch-switch` (popup đổi branch, mở từ status bar), `tmux-prefix`, `open-vscode`, `open-file` (cmd-p, dialog tự vẽ khung), `ui-gallery` (UI kit gallery dialog), `mermaid-board` (dialog Mermaid ở status bar; không phải mod shipped, đừng đưa vào danh sách SHIPPED của `scripts/check-dialog-frames.mjs`), `inbox` (hòm thư: agent cần bạn / chạy xong, review và CI trên PR của bạn; bấm để nhảy tới agent hoặc mở dialog Pull requests (`pr-flow`) đúng PR đó).
- Layouts `main`, `terminals` and `win98` are shipped; `tiendvd-layout` is the personal one.
- Each mod folder has its own copy of `gpui-kit.d.ts` and a generated `jsconfig.json` (`checkJs`, `strict`). Expect many editor type errors that are not runtime bugs: `herdr.d.ts` types `theme()` as `Record<string,string>` while gpui-kit colors want `` `#${string}` ``, and `layout()` / `shared()` return `unknown`. `herdr-app check` is the real gate.

## Mod conventions worth knowing

- `render()` must not call `cx.notify()`; spawn the work (`cx.spawn`) and notify when it finishes. Never keep a `cx` for later use. No `setTimeout`/`setInterval`: use `cx.timer`. Animate natively (`.frames`, `.spin`, `.loop`), never with a timer.
- `issues` keeps per-space state (repo, filters, search, open issue) in `localStorage` key `spaces`, and fetches through the `gh` CLI. New spaces default to state Open and Mine (`fresh()` in `mods/issues/main.js`). `mods/issues/.diagrams/` is a gitignored render cache.
- `git-graph` comes from upstream (rabeeh-ta/herdr-git-graph; `update.js` offers updates) and carries a local dialog patch: `overlay` in `mod.json`, `close()` in `main.js`, the `git-graph.dialog` flag and dialog frame in `graph.js`, `frame: "none"` + `dialogFrame` on the action and update dialogs (`act.js`, `dialog.js`, `update.js`); plus project skills for its row menu's New Claude tab (`key` on the `newTab` action in `git.js`, `agentArgv` in `menu.js`, synced `project-skills.js`; spec 023). Re-apply it after an upstream update.
- `pr-flow` as a dialog closes itself when it opens its viewer pane (the pane would sit under the dialog).
- `pr-flow`'s list is the space repo's PRs of the chosen view, count first (one GraphQL query gives both the Open and Merged chip numbers; header `shown / total`; 0 = empty state, no list call), then 20 rows per page from one GraphQL search by cursor (`page()` in `lib/pr-gh.js`), more on scrolling to the end; Mine ORs every logged-in login as `author:`. Rows from a page are `partial` (no files, body, thread comments): opening a PR fetches it in full. Only the opened PR and agents' branches are polled; a shown view reloads every 2 min. Spec: `specs/019-pr-list-paging/`. Since spec 022 (`specs/022-pr-graphql-batching/`) these reads are combined GraphQL queries in `lib/pr-gh.js`: `discoverMany` looks up all agent branches of a repo in one query, open and merged as separate aliases (found PRs are only tracked; the round's read fetches them; a failed branch is asked again after 30 s), `readPrs` reads up to 10 PRs of a repo per query (replaces `gh pr view` + threads; the inbox and the diff view's comments use it too), and `gh api graphql` answers with errors (exit 1) are read per alias. Actions runs/jobs, logs, diff, merge and comments keep their own calls.
- `reviewer` is split into `main.js`, `dialog.js`, `highlight.js`, `ask.js`, `palette.js`; `issues` and `file-icons` share `lib/markdown.js` (markdown + mermaid diagrams drawn by `mmdc` + fenced code colored by highlight.js via `lib/code-highlight.js` and `lib/vendor/highlight.min.js`) and `lib/diagram-viewer.js` (zoomable dialog overlay of the same mod), synced by `scripts/sync-github-lib.sh`.

## Per-project Claude skills

`.agents/skills/<name>/SKILL.md` and `mcp/<name>.json` (one server config per file, secrets only as `${VAR}`) are a tracked library, not loaded globally (Claude Code does not read `.agents/skills/` by itself). Hand-made skills are put there by hand; third-party ones come from the `skills` CLI run in the repo root: `npx skills add <owner/repo> -s '*' -a universal -y` (the `universal` target writes only `.agents/skills/`), `npx skills update`, and `npx skills remove <name> -y` (without `-a`: `-a universal` prints Done but removes nothing). `skills-lock.json` records CLI installs (ponytail so far). The library moved there from `skills/` with `scripts/migrate-agents-skills.mjs` (spec 015; safe to rerun, it only re-points project links). Project Settings › Skills turns single items on per git project: it saves `projects/<slug>/skills.json` and at once syncs the project's one shared plugin folder `projects/<slug>/claude-plugin/` in place (symlinks into `.agents/skills/`, merged `.mcp.json`, generated `plugin.json`; only changed links are added or removed). The + menu's Claude row (click or digit) syncs that folder again and starts `claude --plugin-dir <that folder>` (skills appear as `herdr-<repo>:<skill>`); all sessions and worktrees of a project share it, so a switch can reach running sessions. The menu decides at launch time through `agentTab` (`mods/my-new-menu/launch.js`, over `agentArgv`), never from a lookup made when it opened: that lookup made a quick cmd-n + digit start Claude plain in main checkouts (spec 027, test in `tests/project-skills.test.mjs`). Leftover per-launch `claude-sessions/<stamp>` folders from spec 012 are removed once no process's command line names them. A worktree is the same project as its main checkout (`projectOf` reads `--git-common-dir`), so it has no selection of its own. The other places that start Claude in a folder attach the set through `agentArgv(agent, folder, machine)` (Claude only, local only, plain argv when nothing is on or on failure with one warning; spec 023): the New worktree dialog's `Start Claude · N skills` chip (`my-worktree`, localStorage `startClaude`, default on; opens the new space with that Claude tab), the git graph row menu's New Claude tab, and the reviewer's Ask. Names outside `[A-Za-z0-9._-]` are listed as invalid. Logic: `lib/project-skills.js` (synced into `project-settings`, `my-new-menu`, `my-worktree`, `git-graph`, `reviewer`). Nothing in Herdr ever writes to `.agents/skills/`, `mcp/` or `~/.claude/`, except Project Settings › Memory, which writes only inside the selected project's `~/.claude/projects/<slug>/memory/` and only on a click. Specs: `specs/012-space-skillsets/`, `specs/013-shared-project-skills/`, `specs/015-agents-skills-library/`, `specs/023-worktree-project-skills/`.

Skill sources (spec 034): `.agents/skills/` holds only Herdr's own skills (ponytail, CLI installs in `skills-lock.json`). Other skill folders are listed per project (spec 035) in its `projects/<slug>/skills.json` (`{ version: 2, sources: ["~/..."], skills, mcp }`; a save of switches keeps `sources`) and scanned after it, for that project only; the first source with a name wins, later same-name folders show as hidden and are never linked. Selections stay names, so a skill can move between sources without touching `skills.json`. The Skills tab's Sources block adds a folder by path (refused: not a folder, already listed, or inside `.agents/skills/`), removes one (says how many of this project's turned-on skills it provided) and marks a missing folder. The SoraTech set (`delivery`, `delivery-*`, `devflow`, `sora-*`, `find-mockup-repo`, `issue-walkthrough`, `onboard-domain`, `translate-requirement`, `archify`, `trace-flow`, `hunk-review`, `mermaid-diagrams`, `playwright-cli`) lives in `~/Documents/SoraTech/skills-set/`, moved there by `scripts/move-skill-set.mjs` (`--dry-run`; safe to rerun; also rewrote their absolute paths into the Herdr home and re-pointed project links; it adds the folder to each project that has a team skill on; the CLI installs among them are recorded in `skills-set/skills-lock.json`, so updating them is a reinstall there by hand). Herdr never writes into a source folder. Every skill row (also hidden and global ones) has an Open button that opens the skill's folder in Zed with its SKILL.md (`zed <folder> <folder>/SKILL.md`, falling back to `open -a Zed`, then Finder); an MCP row opens its JSON (spec 036). The shared `skill-sources.json` of spec 034 was carried over into the projects by `scripts/project-skill-sources.mjs` and deleted. Tests: `tests/skill-sources.test.mjs`.

## Claude threads (right panel)

`threads` lists Claude Code's saved conversations of the space's current folder (`~/.claude/projects/<slug>/*.jsonl`, summaries by one `rg` call, cached by mtime+size, refreshed every 4 s while shown), newest first. Click resumes in a new tab of the same space (`agentArgv` + `--resume <id>`, so project skills attach); a thread live in a terminal (its foreground pid ↔ `~/.claude/sessions/<pid>.json`) is marked running and click focuses it. Rows sit in a virtual list, which takes no per-row handlers: right-click arms a delete, a click on the armed row deletes (`.jsonl` + side folder). Search per space in `localStorage`. Opened from the tab bar's Claude button. Logic: `lib/claude-threads.js` (synced, tests in `tests/claude-threads.test.mjs`). Spec: `specs/031-claude-threads/`.

## Codebase index (Project Settings › Index)

The Index tab shows whether the selected project has a CodeGraph index (`<main>/.codegraph/`) with files, symbols and last index time, and only on a click runs `codegraph init <main>` (Index codebase) or `codegraph sync <main>` (Update index) in the background (one run per project; it outlives the dialog). Before `init` it adds `.codegraph/` to the repo's local exclude list (`git rev-parse --git-path info/exclude`, shared by worktrees), never to `.gitignore`; an untracked, non-ignored index gets an `Ignore in git` button. `codegraph` is looked up on PATH, then `~/.local/bin`, then `zsh -ilc`. Logic: `lib/codegraph.js` (injected `exec` + io, synced into `project-settings`, tests in `tests/codegraph.test.mjs`). Spec: `specs/026-codebase-index/`.

## Claude memory (Project Settings › Memory)

The Memory tab manages Claude Code's auto-memory of the selected project: `~/.claude/projects/<slug>/memory/` of the main checkout (slug = path with every non-alphanumeric character as `-`; worktrees share it). It lists notes (name, description, type from the `---` header, top-level or under `metadata:`; age), filters by type and search, edits a note in place (save refused when the file changed on disk, then Load disk version), deletes with a two-step confirm (its `MEMORY.md` lines go too), flags notes `MEMORY.md` does not link and links to missing notes with one-click fixes, and adds notes in Claude's format plus one index line. Unsaved edits are guarded on note/tab/project switch. Refreshes every 4 s while shown (mtime list first). Logic: `lib/claude-memory.js` (injected `exec` + io, synced into `project-settings`, tests in `tests/claude-memory.test.mjs`). Spec: `specs/029-project-claude-memory/`.

## MCP servers in this repo

Servers whose code lives here go in `mcp-servers/<name>/` (outside `mods/`, so nothing hot-reloads or docks; outside `mcp/`, which only holds library config files the Skills tab lists). `mcp-servers/herdr-ports/server.mjs` is a dependency-free Node stdio server (hand-written JSON-RPC, no `npm install`) with read-only tools `project_ports` (worktrees and listening ports of a project; default = the session's folder, or a folder / project name) and `port_lookup` (free, or who holds a port). It is registered as `mcp/herdr-ports.json` and turned on per project in Project Settings › Skills. Port discovery has one source, `lib/ports.js` (injected `exec`, no `herdr` import): the Ports tab uses its synced copy, the server imports it directly. Herdr terminal names come from `hc ls` / `hc get`; project names from `hc ls` folders. Spec: `specs/014-ports-mcp/`.

## Shared behaviour

The panels follow the focused terminal's folder (`lib/space-folder.js`, copied into mods by `scripts/sync-github-lib.sh`); there is no pinned per-space folder any more. Project Settings lists the git projects of every terminal's live folder in local spaces (Herdr's `space.folder` only for a space with no terminal yet, since it is where the space started and goes stale), and opens on the focused terminal's project. `gh` calls in `pr-flow`, `better-sidebar` and `issues` pick the gh account by repo owner (`lib/gh-account.js`); keep the work account active.


UI kit (spec 018): every personal screen takes its buttons and common surfaces from `lib/panel-ui.js` (synced into each user; add new users to `scripts/sync-github-lib.sh`). `btn(id, {kind, size, label, icon, extra, on, disabled, busy, attention, tip, color, action})` with kinds primary / secondary / ghost / danger / icon / chip and sizes sm 22 / md 26 / lg 32; hover is a highlight layer fading in (120 ms), press an opacity dip (80 ms), busy a spinner, attention a slow accent pulse, all native. The old helpers (`iconButton`, `backButton`, `chip`, `button`, `textButton`) are wrappers over `btn`. Tokens in `UI` (heights, radius, text, space, motion); surfaces `dialogFrame`, `card`, `inputFrame`, `divider`, `sectionTitle`, `headerRow`, `emptyState`. Icons: names in `lib/icons/` or an svg path. List rows, tabs and tree items keep their own look. See everything in the gallery: `herdr-app do mod.open '{"name":"ui-gallery"}'` (`mods/ui-gallery`, never docked).

There is no `docs/` folder (removed on purpose). Behaviour notes for a mod go in this file, short, and a spec-kit feature keeps its detail in `specs/<nnn>-<feature>/`. Never write notes under `mods/` (saving there hot-reloads the mod).
