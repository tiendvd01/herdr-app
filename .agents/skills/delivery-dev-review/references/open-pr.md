# delivery-dev-review · Review một PR đã mở

**Nạp khi:** phase được gọi trên một PR/MR **đã mở** (`/devflow review <PR-url>`), hoặc không có thư mục task trong vault (`SoraVaults/<project>/issue <n>/`) cho PR đó.

Phần mở rộng của `../SKILL.md` (Phase 10). Core giữ template, severity và gate; file này là **cách làm**. Nạp xong thì ghi tên file vào dòng `References đã nạp` ở mục _Scope_ của `review.md`.

## When invoked on an already-open PR

The pipeline runs this phase **before** the PR exists — but the developer can also point it at a PR that is **already open** (`/devflow review <PR-url>` on a live PR). Then the "before the PR exists" assumptions above are inverted. Follow this branch:

- **Diff source is the PR, not the working tree.** Pull it from GitHub at the PR's head sha (`gh pr diff`, or the `get_pull_request` / `get_pull_request_files` MCP tools) with base = the PR's base branch. The working tree may be on a different branch entirely. Still do §5 "đọc ngoài diff" — fetch the branch locally (`git fetch origin pull/<n>/head`) when you need to trace consumers or run the toolchain.
- **Pin the real head, and verify on it — see `delivery-pr-review` §8C.3–8C.5.** Record base/head/merge-base SHA; the head must be the PR's live head sha from the host, never a stale local ref (if you cannot fetch, say `UNKNOWN`, don't call a local ref "the current head"). Verify in a **detached worktree** on that sha; when the head object isn't local and fetch is blocked, **reconstruct** it (base + PR diff) and confirm **every changed file's blob-sha** before trusting the tree — the files API paginates (30/page), so re-review on a partial reconstruction goes red for missing files, not for the PR. **Re-confirm any finding carried from an earlier review at the current head** (a later commit may have fixed it — a "stale finding"). Run the toolchain under the repo's declared runtime (`.nvmrc` / `engines` / `uv`) before blaming a failure on the PR, and tag each finding runtime-reproduced / code-path-proof / counterexample / UNKNOWN (§8C.5).
- **GitLab MR.** Same branch, different CLI: `glab mr view <n> --output json`, `glab mr diff <n>`; SHAs (`base_sha`/`head_sha`/`start_sha`) from `glab api "projects/:id/merge_requests/<n>/versions"` (newest entry). Local fallback: `git fetch origin <source> && git diff <target>...<source>`.
- **Exported PR file in the workspace.** If the PR was already exported to a local file (an agent scratch dir, or the task folder for this PR), read it directly — paginate/grep, it is long — instead of refetching. Trust the head sha it pins only when its fetch timestamp is newer than the PR's latest activity; otherwise treat its diff/comments as stale and re-check against the host.
- **Description ↔ diff.** Compare the PR title/body to the real diff — descriptions often name files, paths or behaviour the code doesn't have. A mismatch is itself a finding (`LOW`/`MEDIUM`): it misleads whoever merges.
- **Existing review threads.** Read the comments/reviews already on the PR (`gh pr view <n> --json comments,reviews`) — don't re-raise a point already made; if you agree with an open thread, reference it instead of duplicating it.
- **There may be no vault task dir (`issue <n>/`).** A PR built outside the delivery-dev workspace has no `plan.md` / `implementation.md` / `status.md`. Fall back to: the issue the PR links (`Refs #…` / `Closes #…` / `Fixes #…`, or the branch name), the repo conventions (`CLAUDE.md`, `.claude/rules/*`), and the **PR's own DoD/description**. Create `12-review.md` in `vault-path.sh "issue <n>"` (or `"pr <n>"` when the PR links no issue) and write the review there as usual. State plainly in the artifact which inputs were missing.
- **CI has not necessarily run.** Do not trust the PR's "lint/build/test pass" claim — check the PR status; if nothing ran (or you cannot see it), run the toolchain yourself on the head per _Chạy toolchain THẬT_ in `../SKILL.md` (bring up the DB via compose; `NOT_RUN` only when you truly cannot). A green-looking DoD is not evidence (§5).
- **Produce `review.md` + verdict exactly as normal.** This phase still does not post on its own.
- **Then hand off — never auto-post.** Because the PR is open, the natural delivery is inline comments on the PR, which is `delivery-pr-review`'s job (invoked directly). Posting to a PR is an **outward-facing action**: draft the review, then post only on the developer's explicit OK. State the hand-off as a concrete next step ("`review.md` ready → post to PR via `delivery-pr-review`?"), not an open-ended question.
